# Blue Current — CPU 性能优化与 GPU 验收加固（V1）

日期：2026-11-09  
范围：`accept:gpu` 真实硬件验收工具、500/1000/2000 鱼 CPU 邻居查询与微热路径。  
不包含：渲染资产改动、Boids 行为重写、Worker/WASM 并行化、邻居数量截断。

## 1. 结论

500 鱼继续作为正式 60 Hz 目标；本机 Intel Iris Xe 的既有硬件验收已经证明该目标可行，四组资产均为 0 丢步、P95 约 12 ms。

1000 与 2000 鱼本轮没有达标，也没有被本轮优化修好。邻居查询的数据结构改进与安全微优化只能带来约 1.05–1.18× 的查询收益，距离 1000 鱼所需的约 2× 仍不足。任何“1000 鱼已恢复 60 FPS”的说法都必须等 Windows 硬件复测，当前证据不支持。

## 2. GPU 验收工具加固

`scripts/gpu-acceptance.ts` 现在把“采样是否可信”作为报告的一部分，而不是只打印 FPS。

| 参数 | 默认值 | 作用 |
| --- | ---: | --- |
| `--warmup-ms` | 3000 | 每次采样前丢弃的预热时间 |
| `--sample-ms` | 10000 | 最短测量窗口 |
| `--max-sample-ms` | 60000 | 等待最少帧数的最长时间 |
| `--min-frames` | 120 | 一个样本被视为充分所需的最少 rAF 帧 |
| `--repeats` | 1 | 每个鱼数的独立重置/采样次数 |
| `--screenshot-timeout` | 60000 | 单张截图超时；0 表示关闭截图 |
| `--uncapped` | 关闭 | 关闭帧率限制与 vsync，仅用于余量测试 |
| `--channel` | 内置 Chromium | 可指定 `chrome` 或 `msedge` |

报告新增 P99、每次重复的独立样本、按鱼数聚合的中位 FPS、最差 P95、中位平均帧时间、样本是否充分，以及完整的验收配置。重复之间会重新设置鱼数并重新预热，避免把上一次的稳定状态带入下一次。

冒烟测试还发现并修复了两个会直接影响可信度的问题：

1. 采样循环会先删除第一帧间隔再判断帧数，导致刚好达到 `--min-frames` 时实际少一帧，所有样本都会被误报为“不充分”。现在多采一帧后再裁剪。
2. 截图超时原本会中断整个场景并丢弃已经测到的样本。现在截图失败只记录为 artifact warning，不影响 FPS/P95 数据和退出码；`--screenshot-timeout=0` 可在无头/CI 环境完全关闭截图。

Windows 正式复测建议：

```bash
npm run accept:gpu -- --counts=500,1000,2000 --warmup-ms=3000 --sample-ms=10000 --max-sample-ms=60000 --min-frames=120 --repeats=3 --channel=chrome
```

需要看未锁帧余量时，单独再跑一次并加 `--uncapped`。锁定显示与不锁帧的结果不能混在同一张表里比较。

## 3. 既有硬件结果

数据来自 `docs/archive/GPU_ACCEPTANCE_2026-11-09.md` 与同目录原始 `results.json`。渲染器为 ANGLE / Intel Iris Xe Graphics / Direct3D11，不是 SwiftShader。

| 鱼数 | FPS | 平均模拟步 | 丢步 | 判断 |
| ---: | --- | ---: | ---: | --- |
| 500 | 122.9–155.7（未锁帧运行） | 8.23–10.47 ms | 0 | 通过，P95 约 12 ms |
| 1000 | 约 7.0 | 17.30–17.92 ms | 29–31 | 未通过；单步已超过 16.67 ms 预算 |
| 2000 | 约 1.7 | 55.60–56.38 ms | 14 | 未通过；每组仅 7 帧，P95 仅作警示 |

后续一次锁定显示的复测给出 500 鱼约 60 FPS、1000 鱼约 6.1–6.7 FPS、2000 鱼约 2.4 FPS，方向一致：500 有余量，1000/2000 的性能悬崖来自 CPU 固定步模拟，而不是 GLB 三角形或 draw calls。

1000 鱼的约 140 ms 帧时间与 `maxSubSteps = 8` 的追赶行为吻合：约 17 ms × 8 ≈ 136 ms，再加渲染。提高 `maxSubSteps` 只会增加单帧 CPU 工作，不能解决预算问题。

## 4. CPU 优化与证据

### 4.1 邻居网格：链表改为按单元连续存储

`UniformGrid3D` 原先每个单元用 `head/next` 链表串起鱼索引。查询时逐个指针跳转，候选距离计算被随机内存访问拖慢。现在每次 `rebuild` 做一次计数排序：统计每个单元的鱼数、前缀和、再把鱼索引连续写入 `cellItems`。`collect` 对每个单元做顺序数组扫描。

邻居集合保持完全一致。临时 A/B 脚本对 500/1000/2000 条鱼的每一条鱼都比较了邻居数量与排序后的索引列表，全部相等。

同一进程内交替运行旧链表与新连续数组，测量“重建 + 全部邻居查询”，取 21 次中的最小值与中位数。宿主为 2 vCPU 沙箱，负载波动很大，最小值比均值更接近真实开销：

| 鱼数 | 链表最小/中位 | 连续数组最小/中位 | 最小加速 |
| ---: | ---: | ---: | ---: |
| 500 | 4.19 / 5.15 ms | 3.74 / 5.16 ms | 1.12× |
| 1000 | 8.42 / 9.39 ms | 8.44 / 10.93 ms | 1.00× |
| 2000 | 41.62 / 91.32 ms | 35.24 / 77.24 ms | 1.18× |

1000 条又单独做了 51 次重复：最小值为 12.58 ms vs 11.95 ms（1.05×），中位数受负载尖峰影响反而变差。结论是数据结构改动安全、在 2000 条有稳定收益，但不构成数量级改善。原始数字见 `test-artifacts/visual-quality-v1/performance-grid-ab.json`。

### 4.2 被否决的缩小单元实验

把单元边长降为查询半径的 1/1.35、1/1.5、1/2，并用查询包围盒遍历，候选检查下降约 10–27%。但在 500 条变慢、1000 条收益不稳定、2000 条只有 2× 单元稳定胜出，整体不能证明净收益。该实验已回退，代码保留“单元边长 = 查询半径、3×3×3 查询”的简单结构。

### 4.3 安全微优化

`ObstacleSystem.computeAvoidance` 增加精确的宽相位：如果当前距离大于“间隙 + 本步最大可能位移”，预测位置不可能进入间隙球，直接跳过该礁石。后续仍使用原来的平方间隙判定与切向力，行为测试保持一致。

`BoidSystem`、`ObstacleSystem` 与 `clampVelocityTurn` 的固定步热路径把 variadic `Math.hypot` 换成显式 `Math.sqrt`，并在转向限制中复用同一次 `cos/sin(maximumAngle)`。`BoidSystem` 的逃逸分支把重复的相位 `Math.sin` 提取为一次计算。这些改动不改变公式，只减少重复求值。

### 4.4 端到端数据为什么不用于结论

官方 `quality:benchmark` 的跨运行数据在同一沙箱内从 500 鱼 6.4–7.9 ms 波动到 9.2–14.4 ms，2000 鱼从 53–62 ms 波动到 95–104 ms。宿主负载（2 vCPU，load average 长期高于核数）足以淹没本轮优化幅度，因此跨运行数字不能用来宣称改进或回归。第 4.1 节的同进程交替 A/B 才是本轮改动的判断依据。

## 5. 验证

| 检查 | 结果 |
| --- | --- |
| Vitest | 24 个测试文件、167 项测试通过 |
| TypeScript `tsc --noEmit` | 通过 |
| Vite production build | 通过；仅有既有的 Three.js chunk 体积提示 |
| Grid / Brute Force 等价 | 通过；连续存储逐邻居比对一致 |

沙箱全量 Vitest 在 7 个 worker 并行时会因 2 核过载让 `SimulationWorld` 的 5 秒默认超时失败；单独运行同文件 2.36 秒通过。建议在沙箱用 `--maxWorkers=1 --testTimeout=60000`，Windows 本地不受此限制。

## 6. 下一步

1000 鱼若要接近 60 Hz，需要的不再是查询微优化，而是架构级选择：把固定步模拟移入 Worker/WASM、在保持行为可验证的前提下限制每鱼邻居数，或降低高密度下的行为更新频率。任何一种都必须重新跑固定种子行为对照与 Grid/Brute Force 等价测试，不能用静默截断或隐藏丢步换取 FPS。

短期正式目标仍是 500 鱼 60 Hz。1000/2000 的 Windows 数据用加固后的命令重新采集，至少 120 帧、3 次重复后再判断。
