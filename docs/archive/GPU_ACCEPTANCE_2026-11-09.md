# Blue Current — 本机硬件 GPU 验收分析（2026-11-09）

## 结论

本次运行已经确认 Blue Current 在 Windows 主机的真实硬件渲染路径上运行，渲染器为 **ANGLE / Intel Iris Xe Graphics / Direct3D11**，不是 SwiftShader。四种资产组合的 500 鱼场景均达到实时目标，硬件截图正常，浏览器错误为 0。

**500 鱼通过；1000 和 2000 鱼未达到实时性能目标。** 性能悬崖主要由 CPU 固定步模拟和密集邻居查询造成，不能归因于 GLB 三角形或 draw calls。2000 鱼每组只有 7 帧，数据可证明当前性能不足，但不足以给出稳定的 P95 尾部估计。

原始证据：`test-artifacts/gpu-acceptance/2026-11-09T08-22-26-230Z/results.json`、`summary.md` 和同目录截图。

| 鱼数 | 四组合 FPS | 平均模拟步 EMA | CPU 渲染提交 | 最新步候选检查 | 丢步与样本判断 |

| 1000 | 约 7.0 | 17.30–17.92 ms | 2.08–2.13 ms | 496758–501572 | 29–31 丢步，29 帧；单步已超过 60 Hz 的 16.67 ms 预算 |

1000 鱼的约 142 ms 平均帧时间与固定步调度器最多执行 8 个子步相符：约 17.3 ms × 8 ≈ 138 ms，再加渲染和其他工作。2000 鱼的模拟步约 56 ms，即使每显示帧只执行一次也无法维持 60 Hz；简单提高 `maxSubSteps` 只会进一步增加每帧 CPU 工作，不是解决方案。

四种资产组合在相同鱼数下的帧率非常接近，draw calls 仅约 51–55，CPU 渲染提交始终约 1.4–3 ms，而候选检查从约 20 万增长到约 191 万。这个对照强烈支持 CPU 邻居搜索／行为计算瓶颈，而不是资产渲染瓶颈。500 鱼之间的高低差不应解释为“GLB 一定比 procedural 更快”，因为各组合并非同时刻、同状态的重复渲染实验。

## 下一阶段优先级

第一步应保持行为不变，拆分并记录 `grid.rebuild`、邻居收集与三项规则、`computeMetrics()`、捕食者和渲染提交的分段 CPU 耗时，确认 2000 鱼普通步与每 30 步详细指标各自占比。

第二步针对密集群体评估更合适的网格单元尺寸与多单元查询、减少无效候选检查，以及将详细群体统计与 60 Hz 行为步进解耦。任何网格改动都必须继续通过 Grid / Brute Force 等价、固定种子、避障和有限值测试；不能通过静默截断邻居或隐藏丢步制造性能提升。

第三步分别测量 Calm 与 Encounter，并增加密度受控的对照场景。当前增加鱼数会继续使用紧凑初始学校，密度与个体数同时变化，优化时需要区分“鱼数增加”和“局部密度增加”的贡献。

最后在本机重新运行相同四组合。2000 鱼应使用更长采样窗口，至少获得 30 帧后再报告稳定 P95；如需 GPU 时间，必须另加真实 GPU timestamp 测量，不能从 `renderMs` 推断。

后续自动摘要已补充 Sim step、Render CPU、Candidates、Dropped steps、Frames 和样本充足性字段，原始 FPS 表保留不变。
